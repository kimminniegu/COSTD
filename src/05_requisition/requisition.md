# 개발요청서 자동변환 · 직접작성 시스템

## 1. 브리핑

해외영업 담당자가 바이어에게 받은 RFP, Product Brief, Development Brief 등의 파일을 업로드하면 필요한 정보를 자동으로 추출하여 사내 개발요청서 형식으로 변환한다.

파일이 없는 경우에는 해외영업 담당자가 동일한 개발요청서 양식을 직접 작성할 수 있다.

자동변환과 직접작성 모두 최종적으로 동일한 개발요청서 결과를 생성하며, 완성된 개발요청서는 PDF 파일로 저장할 수 있다.

# 3. 화면 전환 원칙

자동변환과 직접작성은 서로 다른 결과 양식을 만들지 않는다.

최종적으로 동일한 Development Request Schema를 사용한다.


자동변환

파일
→ 자동 추출
→ 언어 변환
→ 필드 매핑
→ 개발요청서
→ 수정 가능
→ PDF


직접작성

빈 개발요청서
→ 사용자 입력
→ 개발요청서
→ PDF


자동변환 결과를 수정할 때도 새로운 양식을 만들지 않고 동일한 개발요청서 구조를 Edit Mode로 전환한다.

# 5. STEP 1 → STEP 2 자동 전환

파일이 정상적으로 업로드되면 별도의 `분석 시작` 버튼을 누르지 않는다.

파일 업로드 자체를 자동변환 Trigger로 사용한다.


파일 업로드
    ↓
파일 인식
    ↓
원문 언어 감지
    ↓
필요 정보 추출
    ↓
선택한 출력 언어로 변환
    ↓
사내 개발요청서 필드 Mapping
    ↓
STEP 2 자동 이동


처리 중에는 다음과 같은 Loading State를 표시할 수 있다.


개발요청서를 변환하고 있습니다.

✓ 파일 확인
✓ 언어 확인
● 개발요청서 작성 중


변환 완료 후 STEP 1 화면 아래에 결과를 붙이지 않는다.

페이지 자체가 STEP 2로 전환되어야 한다.

# 7. 자동변환 원칙

업로드된 RFP 전체를 그대로 번역하여 보여주는 것이 아니다.

다음 과정을 거친다.


원문 문서
    ↓
필요 정보 추출
    ↓
언어 변환
    ↓
사내 용어 변환
    ↓
표준 필드 Mapping
    ↓
개발요청서 생성


사용자 화면에는 원문과 변환 결과를 좌우 비교 형태로 보여주지 않는다.

변환된 개발요청서만 보여준다.

원문은 추적성을 위해 시스템 내부 데이터로 보관할 수 있다.

# 16. 목표 가격대

연구소용 개발요청서에는 상세 Target Cost를 표시하지 않는다.

다음 세 단계만 사용한다.


○ 저가

○ 중가

○ 고가


자동변환 문서에 Target Cost가 존재하더라도 사내 가격대 Mapping 기준이 있을 때만 자동변환한다.

기준이 없는 경우 임의 판단하지 않고 `확인 필요`로 처리한다.

# 17. 수출 대상국

수출 대상국은 개발요청서 기본정보에 항상 표시한다.

Edit Mode에서는 복수 선택이 가능하다.


수출 대상국 *

[ 미국 × ] [ 캐나다 × ] [ + 국가 추가 ]


자동변환 시 원문에 Distribution Countries 등의 정보가 명확하게 존재하면 해당 국가를 매핑한다.

없으면 임의로 생성하지 않는다.

# 18. 수출 금지 원료

수출 금지 원료 역시 기본정보에 표시한다.


수출 금지 원료

[ Talc × ] [ + 원료 입력 ]


자동변환 시 원문에 명확한 `DO NOT USE`, 금지/배제 원료 정보가 있으면 값을 가져올 수 있다.

단, 바이어가 사용하지 말라고 지정한 원료와 특정 국가 법규상 금지된 원료는 내부적으로 구분한다.


buyer_prohibited_ingredients

regulatory_restricted_ingredients


국가 규제 정보가 최신 기준으로 확인되지 않은 경우 시스템이 임의로 `사용 금지` 또는 `수출 불가`로 확정하지 않는다.

다음 상태를 사용한다.


⚠ 규제 확인 필요

# 21. STEP 4 — 개발요청서 직접작성

## 목적

바이어의 요청을 이메일, 전화, 미팅 등으로 받아 별도의 RFP 파일이 없는 경우 해외영업 담당자가 직접 개발요청서를 작성한다.

STEP 3 Edit Mode와 동일한 Layout과 Component를 사용한다.

# 37. 핵심 구현 규칙

### Rule 1

파일 업로드가 완료되면 자동변환을 시작하고 STEP 2로 자동 이동한다.

별도의 `분석 시작` 버튼을 요구하지 않는다.


### Rule 2

STEP 2는 Read Only Result 화면이다.


### Rule 3

STEP 2의 `수정` 버튼은 STEP 3 Edit Mode로 이동한다.


### Rule 4

STEP 3의 `수정 완료`는 변경된 데이터를 저장하고 Result Mode로 돌아간다.


### Rule 5

STEP 1의 `직접 작성` 버튼은 STEP 4로 이동한다.


### Rule 6

STEP 4는 STEP 3과 동일한 Form Component를 사용하되 빈 데이터로 시작한다.


### Rule 7

STEP 4의 `작성 완료`를 누르면 개발요청서 Result를 생성한다.


### Rule 8

자동변환과 직접작성 결과 모두 동일한 Result Layout을 사용한다.


### Rule 9

Result 화면에서 PDF 저장이 가능해야 한다.


### Rule 10

PDF는 항상 가장 최근 사용자가 확인하거나 수정한 최종값을 사용한다.

# 38. 최종 UX 요약

본 기능의 최종 사용자 경험은 다음 한 줄로 정의한다.


자동변환:
파일 업로드 → 자동변환 → 개발요청서 확인 → 수정 → PDF 저장


직접작성:
직접 작성 → 개발요청서 입력 → 작성 완료 → 개발요청서 확인 → PDF 저장


자동변환과 직접작성의 차이는 `데이터가 어떻게 처음 입력되는가`뿐이다.

두 경로 모두 동일한 개발요청서 Schema, 동일한 Result 화면, 동일한 수정 화면, 동일한 PDF 출력 구조를 사용한다.

이를 통해 해외영업 담당자는 바이어 문서가 있을 때는 업로드만으로 개발요청서를 만들 수 있고, 별도의 문서가 없을 때는 동일한 양식을 직접 작성하여 연구소·공장에 전달할 수 있다.
